## Context

채팅 이미지는 private Supabase Storage에 저장되며, 메시지를 조회할 때마다 클라이언트가 1시간짜리 signed URL을 새로 발급한다. Flutter의 현재 `Image.network` 메모리 캐시는 실행 중 동일 URL에는 효과가 있지만 재접속 후 바뀐 signed URL에는 안정적으로 재사용되지 않는다. 또한 첨부 테이블과 메시지 모델에 이미지 크기가 없어 UI는 다운로드 중 `120×120` placeholder를 표시한 뒤 실제 이미지 비율로 다시 배치한다.

기존 `expand-chat-capabilities` 설계는 `width`와 `height`를 첨부 메타데이터로 계획했지만 실제 migration, RPC와 모델에는 반영되지 않았다. 이미지 객체는 방 참여자만 읽을 수 있어야 하므로 공개 URL 전환이나 영구 URL 저장은 허용하지 않는다.

## Goals / Non-Goals

**Goals:**

- 새 이미지의 정확한 종횡비를 다운로드 전에 확보하여 메시지 목록 높이를 안정화한다.
- 동일 브라우저의 재접속에서 이미 받은 이미지 바이트를 재사용한다.
- signed URL 교체와 무관한 캐시 키를 사용하면서 private Storage 접근 제어를 유지한다.
- 캐시 누락, 손상, 브라우저 퇴거와 URL 만료를 자동 복구한다.
- 캐시 용량을 제한하고 로그아웃 시 비공개 이미지 데이터를 정리한다.
- 크기 정보가 없는 기존 첨부와 영속 캐시를 지원하지 않는 플랫폼을 계속 표시한다.

**Non-Goals:**

- 이미지 버킷 공개 전환 또는 영구 다운로드 URL 제공
- 원본 이미지의 서버 측 리사이즈·압축·썸네일 생성
- 여러 기기 사이의 로컬 캐시 동기화
- 모든 기존 이미지의 서버 측 일괄 크기 분석
- 브라우저가 저장 공간을 퇴거한 이후에도 오프라인 표시를 보장하는 기능

## Decisions

### 첨부에 nullable 크기 메타데이터 저장

`message_attachments`에 양수인 nullable `width`와 `height`를 추가한다. 업로드 전 Flutter 이미지 디코더로 실제 픽셀 크기를 확인하고 `create_image_message` RPC에 함께 전달한다. 메시지 조회 RPC는 attachment ID, 크기와 기존 Storage 정보를 반환하고 `ChatMessage`가 이를 보유한다.

컬럼을 nullable로 두어 기존 첨부를 별도 backfill 없이 호환한다. 새 데이터부터 크기를 필수로 전달하되 기존 RPC 호출과 배포 순서의 호환성을 위해 데이터베이스 함수 전환은 기본값 또는 버전 교체 절차를 사용한다.

대안으로 클라이언트에서 매번 이미지 헤더를 먼저 내려받는 방식은 네트워크 요청을 제거하지 못하고 레이아웃 확정도 늦어 제외한다.

### 저장된 종횡비로 이미지 영역을 먼저 예약

UI는 `width / height`를 현재 버블의 최소·최대 제약 안에서 계산하여 로딩 placeholder와 최종 이미지에 동일한 크기를 적용한다. 실제 바이트를 디코드해도 컨테이너 크기는 바꾸지 않는다.

기존 첨부처럼 크기가 없으면 현재와 호환되는 제한된 기본 비율을 사용한다. 이미지가 성공적으로 디코드되면 측정한 비율을 로컬 캐시 인덱스에 기록하여 다음 접속부터 안정된 크기를 재사용한다. DB를 클라이언트에서 사후 수정하도록 허용하는 대안은 첨부 무결성과 RLS 범위를 넓히므로 채택하지 않는다.

### signed URL이 아닌 attachment ID를 캐시 키로 사용

캐시 키는 immutable attachment ID와 캐시 스키마 버전으로 구성한다. attachment ID가 없는 과도기 데이터에는 Storage bucket/path의 안정적 조합을 사용한다. signed URL의 토큰과 만료 쿼리는 키에 포함하지 않는다.

이를 통해 URL이 매 접속마다 달라져도 동일 첨부의 바이트는 같은 캐시 항목으로 해석된다. Storage path는 객체 교체를 허용하지 않는 현재 업로드 정책과 함께 사용하므로 캐시 무효화 충돌을 피할 수 있다.

### Web 영속 캐시와 플랫폼 fallback을 추상화

`PersistentChatImageCache` 인터페이스를 두고 Web 구현은 Cache Storage에 응답 바이트를, 작은 인덱스에는 사용자 ID, MIME type, byte size, width, height, 생성·최근 접근 시각을 저장한다. 메시지 조회는 첨부 식별자를 먼저 반환하며 앱은 캐시를 먼저 조회하고 miss일 때만 signed URL을 지연 발급하여 다운로드·검증 후 원자적으로 캐시에 넣는다. 캐시 hit에서도 signed URL을 미리 발급하는 구조는 Storage API 요청을 유지하므로 허용하지 않는다.

표시 계층에는 캐시 바이트로 만든 Blob URL 또는 메모리 바이트를 전달하며 위젯 해제 시 임시 Blob URL을 revoke한다. 영속 저장소를 지원하지 않거나 캐시 작업이 실패한 환경에서는 기존 signed URL `Image.network` 경로로 자동 fallback한다. 일반 네트워크 이미지 캐시 패키지만 추가하는 대안은 Web 재접속과 URL 교체에 대한 영속 동작을 보장하지 않아 제외한다.

### 제한된 LRU 정리와 사용자별 삭제

초기 기본값은 최대 64MB와 최대 100개 항목으로 두고, 지원 환경에서는 추정된 브라우저 quota의 20%보다 큰 값을 사용하지 않는다. 삽입 시 최근 접근 순으로 한도를 넘은 항목을 삭제한다. 브라우저 quota 오류가 발생하면 오래된 항목을 정리한 뒤 한 번 재시도하고, 실패해도 화면 표시는 네트워크 fallback으로 계속한다. 접근 시각은 메모리에서 갱신하고 debounce된 일괄 쓰기로 인덱스 저장 횟수를 제한하며 LRU 정리는 삽입 시에만 수행한다.

캐시 인덱스는 소유 사용자 ID를 기록한다. 로그아웃 완료 전에 현재 사용자의 채팅 이미지 캐시를 삭제하며, 캐시 정리 실패가 로그아웃을 막지는 않는다. 동일 브라우저에서 다른 익명 사용자가 로그인해 이전 사용자의 private 이미지를 캐시에서 보는 일을 방지하기 위해 캐시 조회도 현재 사용자 ID 일치를 요구한다.

### 동시 요청을 합치고 실패 결과는 캐시하지 않음

동일 키에 대한 진행 중 다운로드는 하나의 Future로 합쳐 목록 재빌드나 상세보기에서 중복 요청하지 않는다. HTTP 실패, 빈 응답, MIME 불일치 또는 decode 실패 결과는 저장하지 않는다. 손상된 기존 항목은 삭제하고 signed URL로 한 번 다시 받아 복구한다.

서로 다른 이미지의 동시 다운로드·디코딩도 기본 4개로 제한하여 긴 대화 진입 시 네트워크와 메모리 급증을 방지한다. 목록 이미지는 표시 크기에 맞는 decode target을 사용하고 원본 해상도 디코딩은 상세보기에서만 허용한다. 캐시 인덱스는 앱 시작 시 전체 Cache Storage를 스캔하지 않고 작은 manifest 하나만 읽는다.

## Risks / Trade-offs

- [브라우저 저장소에 private 이미지가 남음] → 사용자 ID로 격리하고 로그아웃 시 삭제하며 용량·보존 범위를 제한한다.
- [브라우저가 Cache Storage를 임의 퇴거함] → 영속 캐시는 최적화로 취급하고 miss 시 signed URL 경로로 복구한다.
- [기존 이미지에는 크기 정보가 없음] → 첫 표시는 기본 비율을 사용하고 성공적으로 측정한 크기를 로컬 인덱스에 저장한다.
- [원본 이미지 캐시가 저장 공간을 빠르게 채움] → 64MB·100개와 quota 20% 중 작은 한도를 적용하고 후속 변경에서 썸네일 생성을 검토한다.
- [고해상도 이미지 동시 디코딩으로 메모리가 급증함] → 목록용 축소 디코딩과 동시 작업 4개 제한을 적용하고 codec·Blob URL을 즉시 해제한다.
- [DB와 Web 클라이언트 배포 순서가 어긋남] → nullable 컬럼과 호환 가능한 RPC 배포 후 클라이언트를 배포하고, 구버전 클라이언트 호출을 테스트한다.
- [Blob URL 생명주기 누수] → 이미지 위젯 단위 소유권을 명확히 하고 dispose 시 revoke하는 테스트를 둔다.

## Migration Plan

1. nullable `width`, `height` 컬럼과 양수 제약을 추가하고 이미지 생성·조회 RPC를 하위 호환 방식으로 갱신한다.
2. Flutter 모델과 업로드 흐름에서 크기를 추출·전달하되 null 응답도 허용한다.
3. 플랫폼 캐시 abstraction, Web 영속 구현과 fallback을 추가한다.
4. 고정 종횡비 placeholder와 캐시 이미지 resolver를 UI에 연결한다.
5. 단위·위젯·Web 통합 테스트와 release 빌드를 실행한다.
6. 데이터베이스 migration을 적용한 뒤 Web 앱을 배포하고 재접속 네트워크 요청·스크롤 안정성을 실제 브라우저에서 검증한다.

롤백 시 Web 앱을 이전 버전으로 되돌릴 수 있다. 추가 컬럼은 nullable이므로 기존 앱에 영향을 주지 않으며 즉시 제거하지 않는다. 캐시 버전 접두사를 변경하거나 시작 시 삭제하여 잘못된 캐시를 무효화한다.

## Open Questions

- 기존 이미지의 최초 표시에서도 이동을 완전히 없애야 한다면 별도 서버 backfill 작업을 수행할지 결정해야 한다.
- 64MB·100개 기본 한도와 quota 20% 정책을 실제 사용 패턴에 맞춰 조정할지 운영 검증이 필요하다.
- 원본 대신 별도 썸네일을 캐시하는 최적화는 트래픽과 화질 측정 후 후속 변경으로 검토한다.
